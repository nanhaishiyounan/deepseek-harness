## Problem

EAM did not exist (equipment ledger, maintenance, checkpoints, calibration — the hub_as_* demo tables were dead) and APS had no bottleneck attribution, load heat, or what-if.

## Decision

### 1. The EAM domain (four collections + the preventive engine + the order state machine + the Andon bridge)
- `eam_assets` (8 pieces of the 速冻水饺 line: mixing/freezing/metal-detection/packing plus thermometer/balance/pH and a scrapped sample; the `ccp_code` column ties the metal detector to CCP-JC-01, the freezer and its thermometer to CCP-SD-01, and the mixer to CCP-XT-01 — the same codes W6-B4's monitoring points carry; `workcenter_id` links the FCS spine so the Andon request auto-attaches the operation's center), `eam_maint_plans` (weekly/monthly frequencies + checklists + next_due_date), `eam_maint_orders` (the one-way CAS machine new→accepted→done→closed; done requires a repair note; close is the requester's or admin's — plan §5.6's requester-verifies rule), `eam_calibrations` (four strong-inspection instruments: the metal detector 10 days overdue = critical, the pH meter 3 days out = critical, the freezer thermometer 14 days out = warning, the balance in date).
- The preventive engine `scanMaintPlans`: every due plan mints one work order per missed period (dedup_key `plan:{id}:{due}`), then advances next_due_date by the frequency (catch-up bounded at 24 periods; a bad period skips with an error line). It rides the engine's hourly alert-scan tick (a not-yet-seeded library is a quiet no-op) plus the manual `POST /eam/scan-plans`.
- The Andon repair request (the B4 placeholder activated): the `cards.html` gear menu enables → `POST /andon/maintenance` (the card-flow session derives the requester; the 生产车间 department fence holds) → attaches the asset by the operation's work center, flips a running asset to `repair`, and mints a P1 order; the assert exercises the full chain (an XSS payload lands verbatim — the rendering-side esc() is the defense, asserted present in the calendar block).
- Fences: maintenance processing (accept/done) is 生产车间 + admin (no dedicated 设备部 exists — the workshop owns the equipment role, and the refusal text names 设备/生产/admin); close is requester-or-admin; buyer is 403 across the chain.

### 2. Two new alert rules (the B2 engine goes to eight)
- `calibration_due` (warn 14 / critical 3, routed 质检部+planner) and `maint_overdue` (planned date passed while still new/accepted; >2 days = critical, routed 生产车间+planner) join `hitsSelect`; the three enum surfaces (both collections' select enums + RULE_TYPE_OPTIONS) move together, and `patchRuleTypeSurface` upgrades the existing pages idempotently (2 fields, 1 column, 2 stat cards on the observed run). A re-calibration or a finished order leaves the rule's scope and the row auto-resolves.

### 3. The APS additions (frePPLe's ideas, no solver)
- **Bottleneck attribution + load heatmap** (`/aps/load`, the APS瓶颈与负荷 JSBlock): load rate = Σ planned_min ÷ (shift span × parallel — `dailyCapacityMinutes`, the same formula FCS applies); a bottleneck is a bucket over 100% that still carries an open operation, listed with the occupying MOs; the WC × 14-day heat matrix (green <80 / amber ≥80 / red ≥100). Reconciliation: the hand-written SQL twin and the engine's own output agree row-for-row (asserted 1 = 1, with the W2-B6 1200-minute > 480-minute/day = 250% bucket in the list).
- **The what-if sandbox** (`/aps/whatif`, pure in-memory): re-plans only status='planned' operations (started/done stay as frozen base load) in (boost first, need_date, code) MO order with same-MO sequencing, the never-straddle boundary, and Sundays + holiday calendars — FCS semantics verbatim; the knobs are per-work-center overtime minutes per day (validated 0-960) and MO boosts. **Zero writes** (the assert proves the mfg_order_operations table md5 is byte-stable across a simulation).
- **Promote** (`/aps/promote`, fenced to 计划部（PMC）/admin): recomputes the same scenario, rewrites planned_date per row under a status='planned' CAS, refreshes the MOs' planned_start/end, and files the params + delta + applied count as an `aps_whatif_runs` audit row (the filed difference report).

### 4. Pitfalls found and fixed (all reproduced before fixing)
- Under `-t -A`, `INSERT/UPDATE … RETURNING` prints rows **followed by the command tag** — `Number('5\nINSERT 0 1')` is NaN; parse the first line (both the promote run id and the /eam/act return code).
- The RunJS authoring validator flags a `render` referenced before its const declaration as an unknown global (hoisted `function paint()` instead) and `instanceof Element` equally (duck-typed check).
- JSBlock interaction order: runSim/promote must **read the knobs before paint()** — paint rebuilds the DOM and resets the inputs to their defaults, so the scenario otherwise always arrives empty.
- `mfg_holidays` columns are `calendar` and `date` (not calendar_id/holiday_date).
- What-if assert rerun tolerance: once a scenario has been promoted, the stored plan already sits at the scenario's dates and a repeat simulation moves nothing — the movement evidence falls back to the first run's filed `delta->moved` (the assert takes either).
- One transient b4-assert normal-report engine_error was observed once and self-healed (ALL PASS twice after, plus a 200 probe at the same state) — a rehearsal-MO remaining-quantity boundary, not a regression of this batch; recorded as observed.
