# Agent Note: Verification-blocker fixes — keyless hang, approval-workflow lease, draft budgets, and model-JSON tolerance

Status: implemented

English | [中文](2026-09-05-r1-verification-blockers.zh.md)

## Problem

The production-readiness verification (overall 77, mandatory code-review 58 FAIL) listed four Go-live blockers. First (F-2): the teardown of demo-full-journey.mts and two e2e files wrote `await new Promise(resolve => server?.close(resolve))` — the optional chain short-circuits when the server never started (the keyless all-SKIP path), the promise never settles, and the process hangs forever; reproduced 2/2. Second (F-3): the expert-orders sections of `expert-order-e2e.cordis.yml` and the production `cordis.patch.yml` omitted `draftMaxTokens`/`draftTimeoutMs`, so the seam default of 4096 tokens truncated the real MiniMax-M3 draft's DraftSpec JSON mid-flight (finish=max-tokens) and failed the order — the demo and nocobase-track compositions had long pinned 16384/120000; three-way config drift. Third (F-4): pausing the production workflow on the real approval track had no ok check on the toggle, the teardown restore swallowed errors with `.catch(() => undefined)`, and the demo's restore condition was "restore production only if the clone was created" — a half-created clone left the production approval flow permanently disabled. Fourth (D-1): `parseDraftResponse` had zero tolerance for model output, so occasional live-stream JSON noise (prose around the JSON, trailing commas, truncation) pushed orders straight into failed — the direct root cause of the nocobase-track e2e's 6/6 failures.

## Decision

### WorkflowLease: pause → operate → restore regardless of outcome (examples/kb-agent/scripts/nocobase-workflow.ts)

The verbatim-duplicated NocoBase workflow operations in the demo and the e2e (pause production, build the four-node private clone, drain stranded approvals, resolve the manual task) moved into a shared module whose core is `WorkflowLease`: `pause()` toggles the production workflow off and sets the `paused` boolean only after the HTTP answer confirms ok (toggle is a flip — an unconfirmed pause is never re-toggled by a restore; a failed pause throws instead of operating on the production flow in reverse); `setClone()` registers the clone id; `restore()` destroys the clone first, then re-enables production, attempts both actions even when one fails, aggregates failures, never swallows, and clears its state on success so a repeated restore re-toggles nothing. The demo's top-level teardown wraps `lease.restore()` in try/catch and records a restore failure as a FAIL scenario row (non-zero exit, transcript still written); the e2e's afterAll records a restore failure and still runs the remaining teardown. `closeHttpServer(server | undefined)` replaces the optional-chaining close trap with an explicit `if (server === undefined) return` and is shared by all four files' teardown. `resolveEnv` was extracted at the same time (three ~150-line duplicates collapsed into one function in `scripts/resolve-env.ts`). The approval-task resolver returns false when no task appears within 30 seconds (the original break semantics) and throws when the submit itself fails.

### Draft double line of defense: parse repair + one error-carrying retry (packages/expert/expert-orders/src/draft.ts + index.ts)

The first line lives inside `parseDraftResponse`: when strict parsing fails, `repairDraftJson` runs first — a single character-scanning pass (tracking string literals and escapes) that strips prose before the JSON, drops trailing commas outside string literals, and appends the missing closing brackets for a tail truncated after a complete value; what it cannot repair keeps the original error and fails loud. The second line lives in the `draftSpec` runtime: a parse failure (one the repair layer could not absorb) re-requests the draft once, carrying the previous parse error (the retry prompt states "the previous output was not valid JSON (<err>)"), each attempt with its own deadline; a second failure lands failed under the existing compensation semantics. `finish !== 'stop'` (max-tokens truncation) and network errors are not retried — retrying a truncation would likely truncate again (the cure is the F-3 budget), and network faults are a transient domain. The order number's random tail widened from 4 to 8 hex (same-day collision space 2¹⁶ → 2³²), with the keyless snapshot's order-number normalizer updated in lockstep.

## Alternatives considered

**Restoring the production workflow inside the demo scenario body's try/finally.** Rejected: the scenario harness already captures assertion errors and the top-level teardown runs on every path; putting the restore in a body finally would fork the "teardown guarantees restore" semantics into two places.

**Deleting trailing commas with a regex (`,\s*[}\]]`).** Rejected: a regex cannot tell a `,]` inside a string literal (paragraph text can contain it) from a real one; the mis-delete would corrupt content. The single scanning pass costs the same order.

**Also retrying finish=max-tokens.** Rejected: truncation is a budget problem, not sampling noise — a retry would likely truncate again and burn another 120s deadline. The budget fix (16384) is the cure; truncation stays a loud failure documented in troubleshooting.

**Fixing `?.close` inline in each e2e instead of extracting a helper.** Rejected: the demo/e2e restore conditions had already forked into one production-disable incident; fixing each separately would copy the same semantics into a third place. The shared module leaves "pause → operate → restore" with exactly one implementation.

## Consequences

- Keyless environment (no MINIMAX_API_KEY, no NocoBase) running demo-full-journey: three scenarios self-skip with explanations, the process exits in 4 seconds (exit code 0), the transcript lands on disk — without `closeHttpServer`'s explicit undefined guard, the same path hangs forever.
- The production composition (cordis.patch.yml) and the e2e fixture now match the demo/nocobase-track drafting budgets (16384/120000); the DraftSpec fits the configured draft budgets without truncation.
- On the real approval track, a half-created clone still guarantees the production workflow is restored; a failed restore is recorded loudly — a FAIL scenario row (demo) or a teardown log line that continues the cleanup (e2e) — and a repeated `restore()` never re-toggles the flip.
- Three noise shapes (prose prefix, trailing commas, bracket-completed truncation) are absorbed without a retry; remaining parse failures consume one error-carrying retry; a second failure still lands failed — never pretending success. The nocobase-track e2e passes green in one measured rerun (6/6 scenarios, 78s end to end).
- Every NocoBase workflow action (toggle/create/destroy/submit) and workflow read (task list, task status) checks HTTP ok; any non-2xx from the NocoBase side fails loud.
- The N7 quality-gate matrix in plans/connector-lakehouse-nocobase/02-batches.md reports the hygiene exemption count truthfully: ~235 `./src/*` exports-pattern exemptions against the pre-existing ~225 baseline, this work line's ten new packages included. Six follow-up debts are registered in the same file's legacy section: the three order-state-machine gaps, the default-preset connector-tools decision, the kb_search filename channel, lakehouse tool-title localization, the work line's per-file coverage gaps, and connector_discover keyword steering.
- QUICKSTART.zh.md's retrieval-threshold wording matches the deployed 0.015 configuration, and its FAQ carries three field-verified entries: the draft max-tokens budgets, the model-JSON repair/retry path, and the keyless demo's SKIP semantics.
- Order-number tails are 8 hex; the `order_create` snapshot is unaffected via normalization (`ORD-<date>-<no>`).
