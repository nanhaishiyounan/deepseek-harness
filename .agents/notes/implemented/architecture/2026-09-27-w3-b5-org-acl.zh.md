# Agent Note: W3-B5 组织与权限（部门树 + 员工挂接 + 角色×集合矩阵 + 审批按部门路由）

Status: implemented

[English](2026-09-27-w3-b5-org-acl.md) | 中文

## 问题

用户反馈：「得有部门员工的一整个权限管理吧」。当时平台没有组织结构（无部门、无用户归属），角色只有 admin/root/b4guard 加一个仅 `view` 的 member 策略，审批引擎的 `approver_map` 只认用户名（W2-B5）——审批档位无法路由到「质检部谁当班谁审」，管理员也没有页面能看到或治理每个角色对每个集合的动作权限。

## 决策

- **不自建 org_departments/org_employees——组织面全部由 plugin-departments 承担。** 快照里的插件（setup 起已启用）提供 `departments` 树（邻接表、`parentId`）、`departmentsUsers` 挂接表、`users.mainDepartmentId`（插件在每次挂接写入后的 afterSave 钩子里自动同步），以及系统设置 → 用户权限 → 部门 下的原生管理页。种子（nocobase-w3-org-acl.mts）落 新源食品集团 → 采购部/计划部（PMC）/生产车间/质检部/仓储部/销售部/行政人事部 加上刻意无成员的 储备人才池（空部门负例素材），把既有演示用户挂上去（quality_lead + 新建的 qc_inspector → 质检部，让部门路由展开成真实的双人档），并回填 `hub_hr_employees.org_dept`（新增 m2o → departments）——花名册页能看到组织部门，事实源仍在 departments/users（旧 `department` m2o → hub_hr_departments 原样保留，属 f3 演示面）。
- **权限矩阵页只读渲染；写入面是 NocoBase 自己的角色编辑器。** JSBlock 经三个 MultiRecordResource 读 `rolesResources`/`rolesResourcesActions`/`roles`，把 角色 × 集合 × view/create/update/destroy/export 渲染成 ✅/—（D7「只读渲染 + 表单直写」分工）。rolesResources 与 rolesResourcesActions 是 plugin-acl 的私有集合——集合管理器里没有行，任何 v2 表格/表单块都会渲染成「可能已被删除」占位——因此直写面就是原生编辑器（系统设置 → 用户权限 → 角色），页面脚注写明入口；JSBlock 的数据面在授了 view/list/get 后读取正常。
- **member 的业务动作矩阵以 rolesResources 行落库，先授权后探针（PLAN 风险 ④）。** view/list/get 沿 B1 授权；create/update 按域补齐——pur_*、仓储单据集合（收发货/移库/盘点）、qm_inspections/qm_inspection_readings（+ qm_nc_dispositions update）、生产执行集合、so_orders、wfl_approval_todos update（act 路径）。引擎独占的台账（wms_stock、wms_movements）与一切 destroy/export 保持 admin 专属。403 翻转探针实证矩阵咬合：把 (admin, wms_counts) 收窄成 view/list/get 后 b4guard 的空 body update 拒 403；补齐动作集合并 touch 一次动作行后恢复 200，库内零残留。
- **部门路由扩展 approver_map 而不触碰纯路径（缺省零漂移）。** 角色值可以是 `{type:'department', value:'质检部'}`（也可与用户名混排数组）。`resolveApproversOfRole`（approval-engine.mts）经 departments/departmentsUsers 把部门展开成成员用户名；纯用户名 map 原封不动交给共享的纯函数 `approversOfRole`——同一 map、同一参数、同一顺序，与 W2 完全一致。部门不存在、部门无成员在提交时 fail-loud；selftest 把纯 map 的展开形态（逐人一行）钉成零漂移断言。qm_nc_dispositions 的 manager 档经 B4 配置中心通道（REST + config_note 留痕）永久路由到 质检部；其见证处置单的 todos 展开为 quality_lead + qc_inspector，任一人 act 全档完成（W2 或签语义）。nb_approve 工具路径仍只解析纯 map——部门形态在那里 fail-loud，因此部门路由只用于页面/CLI 驱动的单据类型。
- **B4 一致性探针识别部门形态。** assertWflConsistency 的审批人存在性检查把 `{type:'department'}` 条目对照 departments/departmentsUsers 校验（存在且非空），不再静默跳过；B4 状态图摘要渲染「部门·质检部」标签；approver_map 表单描述写明该形态。

## 后果

- 真实操作者能维护组织（原生设置页）、看见组织（组织架构页的 SVG 图 + #id 标注 + departments/users 表），并从一页治理逐集合动作；员工花名册显示组织部门。
- 审批引擎能把一个档位路由到部门而不点名用户；departmentsUsers 里的人事变动自动改变后续单据的路由，无需改配置。
- member 用户在其域内获得真实业务写动作，而台账旁路守卫与 destroy/export 仍 admin 专属；翻转探针 + verify 的零残留断言持续把关。
- setup-nocobase verify 从 org-acl 脚本导入 `collectOrgAclFailures`——树/挂接对拍、页面 wire、矩阵菜单 admin 专属、member 动作下限、部门路由见证、（如今识别部门的）B4 探针一个口径。

## 现场踩坑

- **plugin-acl 只在 `rolesResources.afterSaveWithAssociations` 与 `rolesResourcesActions.afterUpdate` 写穿运行时 ACL。** 没有 afterDestroy 监听（销毁资源行后窄化的运行时面仍然活着），动作行 CREATE 也不写穿——授权后必须 touch 一个动作行（update）让重写重新读全部动作；403 翻转探针和每个授权助手都以该 touch 收尾。
- **动作行的 `fields` 为 `[]` 会隐藏所有列**（list 返回 200 但零行）——B1「显式全字段清单」惯例只适用于集合管理器里真有字段行的集合；没有就保持 fields 为 null，绝不写空数组。
- **pm.departments snippet 只声明可配置动作，不授予任何东西。** admin 角色的策略是 create/view/update/destroy/export/importXlsx——没有 list/get；而 root 用户的唯一角色是 root、策略为 null（一切靠显式资源行）。组织图因此对 admin/member/root 授 departments/departmentsUsers 的 view/list/get、对 admin/root 再加三个 ACL 集合；缺了这些 JSBlock 会在 403 上中途死掉。
- **私有插件集合承载不了 v2 块。** departmentsUsers 与 rolesResources/rolesResourcesActions 在库里存在、REST 应答，但集合管理器没有行（collections:create 拒绝「already exists」），表格块渲染成已删除占位——这些面经插件自身 UI 或 REST 通道编辑。
- **浏览器会话的角色是请求头，不是猜测。** 诊断中途无 `X-Role` 的页面内 fetch 一律 401/空，会话过期更让一切渲染像坏了；先拿 `X-Role: <role>` + 新 bearer token 探明再怪线上。
- **destroyDepartmentCheck 拒绝删除仍有成员的部门**——两行无 title 的安装残留（#4/#6，都挂着 zhaoxiaofang）清不掉；它们在部门表里渲染成两行空行，组织图按 title 过滤不显示（待 W4 把残留挂接迁走后清理）。
- **重复 build 叠出了重复的花名册列**——org_dept 存在性检查命中列，但 rollback 后重建的循环仍铸了三列；销毁多余的 TableColumnModel 行清扫（保留一列）。users 表 `mainDepartment.title` 列路径在 v2 列线束下渲染不出，弃用改靠组织图的 #id 映射。

## 备选方案

**自建 org_departments/org_employees。** 否（PLAN D7、能力盘点 §4）：插件的集合、同步钩子、管理页已覆盖整个面；第二花名册会分叉事实源。

**矩阵页直写 rolesResources/rolesResourcesActions 表格。** 平台否决而非偏好：私有集合承载不了 v2 块。原生角色编辑器是写入面，JSBlock 是可视化。

**nb_approve 也路由部门。** 缓议：工具路径共享纯规则模块，给它做无 IO 的部门展开意味着扩大工具的数据访问；部门路由的 qm_nc_dispositions 走页面/CLI，边界以文档说明。
