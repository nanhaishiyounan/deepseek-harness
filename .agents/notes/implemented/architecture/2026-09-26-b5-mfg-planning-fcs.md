# Agent Note: B5 manufacturing planning foundation — BOM versioning, work-center calendars, the approved ≠ released split, and the day-bucket greedy scheduler

Status: implemented

English | [中文](2026-09-26-b5-mfg-planning-fcs.zh.md)

## Problem

After B4 the manufacturing domain was entirely absent: no BOMs (recipe/usage/scrap), no work centers or capacity calendars, no manufacturing orders, and no scheduling. Batch 06-b5 requires the planning layer — manufacturing master data + manufacturing orders on the B1 approval engine + a finite-capacity scheduler isomorphic to ERPNext's official capacity planning (day-bucket greedy, operations never straddle days, busy centers queue or switch to the alternative). Three design points had to land: the approval-versus-release relationship (approved ≠ released), the what-if triple (Preview → Apply → freeze), and the "no MO without an active BOM" creation gate.

## Decision

- **BOM versioning and effectivity**: `mfg_boms` rides its own `bom_status` axis (draft→active→retired — not the B1 six-state machine; a BOM is master data, not an approval document), and version switching never deletes the old row (the seeded BOM-0001 stays retired for audit). The MO-creation gate is a set gate (`wfl_gate_configs`: downstream=mfg_orders, upstream=mfg_boms, upstream_field=bom_id, upstream_state_field=bom_status, required_status=active) — nb_create and the engine's `enforceGates` refuse from the same source; retired/draft BOMs never pass.
- **Routing inlined in the BOM (the Odoo scheme)**: `mfg_bom_operations` hangs off bom_id with seq / work center / setup minutes / per-batch run minutes / batch size / alternative work center (nullable). No separate Routing table — matching the existing MES research conclusion.
- **approved ≠ released**: the MO's doc_status approval segment fully reuses the B1 six-state vocabulary (`seedDocFlow(io, 'mfg_orders', …, { amountField: 'estimated_cost' })`; qty×std_cost above ¥100k adds the GM round). released/closed are **post-approval business terminals** — outside the approval vocabulary, never through `act()`; the scheduler's `--release` writes them under an optimistic conditional (approved→released + released_at backfill) and automatically runs one preview into `mfg_orders.preview_data` (the release push for the mobile read side). The orthogonal `reservation_state` (none/partial/assigned) stays for B6. Rationale: release is a dispatch action, not an approval action (`act()` accepts only approve/reject/void), and close is a completion action (B6) — forcing them into the shared six-state machine would pollute every other document type.
- **Day-bucket greedy scheduling (`mfg-schedule.mts`)**: a pure core (planForward/planBackward) plus REST CLI verbs. Duration `planned_min = setup_min + ceil(qty/batch_size) × run_min × 100 / efficiency_pct` (Odoo time_efficiency + ERPNext batch amortization). Daily capacity = shift-span minutes × capacity_parallel; Sundays and the work center's holiday calendar (mfg_holidays rows shared by the calendar column) are non-working. Forward: from max(today, released_at) each operation finds a slot, a successor's scan starts no earlier than its predecessor's day; three consecutive full working days on the primary center switch to alt_workcenter (Odoo alternative_workcenters); fourteen consecutive full days land the overload marker. Occupancy buckets are `wcId:date → Σplanned_min`; cross-MO conflict queues read the same bucket table (apply order serializes the queue).
- **Preview/Apply freeze semantics (the what-if triple)**: `--preview` computes JSON and writes nothing (approved/released may look; draft/pending always refuse — not effective, no scheduling). `--apply` requires released (approved also refuses — the two-state gate), writes `mfg_order_operations` + planned_start/end; an applied MO refuses a second apply (frozen) and rescheduling must `--void` first. `--latest-start` walks the critical path backward from need_date; a first-operation latest start before today raises the negative-slack warning (建议改期/拆单/外协).
- **The never-straddle product boundary (contract wording)**: a duration above one day's total capacity **never fits** — the overload marker plus the 拆单/外协 advice; an operation is never split across two days (ERPNext's own constraint). This is a product boundary to communicate up front, not an implementation detail.
- **mobile trio**: formRegistry +2 (the simplified BOM head / the manufacturing order; component lines and operations live on the platform), persona registry entries 11/12 plus the manufacturing read skill (MO status query with four metrics — approval state / release date / planned start / planned end; schedule query with a three-level fallback — operations rows → preview_data snapshot → the honest "not released or not scheduled yet").

## Notes

- **The no-new-vocabulary ruling**: the task brief said the vocabulary mechanism could grow a manufacturing family; the implementation declines — the MO's approval segment is exactly isomorphic to the six-state machine (draft→pending→`level2`→approved) with no new approval states, while released/closed are post-approval advances (same as w3's RFQ sent/closed and PR converted precedents: engine-CLI conditional `updateWhere`, never `act()`). A new state_field family would require `vocabularyForStateField` registration, `readState` dispatch, and nb_approve tool-surface sync — all cost with no semantic increment.
- **Calendar traversal trap**: the per-day scan in `tryPlace` must check isWorkingDay **every step** (Sundays/holidays skip without counting as queue days) — the first version rolled only once at entry, and selftest ③'s "9-27 Sunday got scheduled" exposed it immediately; the selftest's date assertions now check Sundays and the seeded holiday explicitly.
- **Backward-pass demo hygiene**: the --latest-start negative-slack demo compresses need_date and must restore it; a crash in the compressed state self-heals by restoring max(original, today+seed-offset), otherwise the compressed date persists and poisons later batches.
- **The LLM code-collision incident**: the mobile MO registration let the model mint a code that collided with an existing one (MO-2026-0002 duplicated on insert) — the persona rule now reads "nb_list the current max NNNN and add 1; never reuse an existing code"; the row was corrected to MO-2026-0003. Code uniqueness currently rests on prompt discipline; if B6 sees it again, an engine-side code-uniqueness guard is due.
- **The preset YAML indentation trap**: new paragraphs inside the persona `text: |` literal block must keep the 6-space indent — one 5-space line produced `bad indentation of a mapping entry (71:6)`, and the failed preset mount shows up as "send does nothing" (session.prompt returns an internal error). Parsing with js-yaml before syncing the `.dsh` copy is a cheap guardrail.
- **Decimal display**: the v2 table's DisplayNumberFieldModel renders three-decimal qty_per_unit values like 0.062 as 0 (column render precision); the stored data is intact (psql shows the original). Precise display is a later rendering-layer polish, not an engine concern.
- **MO-2026-0003 (built over mobile) stays draft**: the conversation-registered order keeps its draft state; the chain demo rides MO-1/MO-2 — the user-visible "registration lands as draft" shape.

## Alternatives considered

- **Infinite-capacity scheduling** — D5 chose the finite day-bucket FCS (queue-or-substitute on conflict); infinite dates would promise what the work centers cannot run.
- **Scheduling arithmetic in a workflow update node** — the ⑪ pitfall: read-modify-write cannot run there; the engine owns it.
- **Cross-day operations inside one bucket** — product boundary (split the order instead), stated up front in contract language.
