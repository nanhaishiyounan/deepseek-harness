# Agent Note: NocoBase real track — wire corrections from a live 2.2.6, the approval workflow, and attachment delivery

Status: implemented

English | [中文](2026-09-05-nocobase-real-track-integration.zh.md)

## Problem

Batches N3–N5 spoke to a mock NocoBase modeled on the research report's REST summary (v1-era). N6 had to make the same DSH code run against a live NocoBase 2.2.6: bring the backend up reproducibly, land the expert-dataset collections and the 张红喜 seed on it, wire order approval through the workflow engine with a request-node callback into the DSH `orders.fulfill` RPC entry, and hang every delivered PDF back on its order row as a real attachment. The mock's wire assumptions had never been tested against a real server.

## Decision

**Treat the live instance as the only wire authority; the mock follows it.** Standing up the source checkout (postgres, `yarn nocobase install`, `dev-server`) and probing each endpoint revealed five divergences from the v1-shaped assumptions, all now encoded in `NocoBaseClient` and mirrored by the mock: (1) the POST body's top level IS the action's values — a `{values: {...}}` wrapper stores a literal `values` field; (2) every JSON response is `{data, ...}`-wrapped and must be unwrapped; (3) list answers `{data: rows, meta: {count, ...}}`, not `{count, rows}`; (4) a missing row answers 200 + `{data: null}`, never 404, so `get` resolves `undefined`; (5) row updates address the record through `POST /api/<collection>:update?filterByTk=<id>` — the v1-style `/<index>:update` path is simply not registered (404). Corrections from the workflow engine run deeper: the collection trigger's config takes a `mode` bitmap (`CREATE: 1`), not an `event` string; a workflow created with `enabled: true` over REST lands without its db hook mounted — one off/on toggle cycle mounts it; the processor scope keys job results by node **key** (`$jobsMapByNodeKey.<uid>._`), not node id; the collection trigger's `$context` is `{data: <row>}`, so the row id is `$context.data.id`; a request node's `contentType` becomes the literal Content-Type header, so it must read `application/json` (the gateway's write fence 415s on anything else); and association loads use plain `?appends=deliverable`, not a JSON object. `setup-nocobase.mts` encodes all of this; its `verify` step asserts the resulting state.

**The approval workflow is four nodes, both manual actions RESOLVED, main chain explicitly linked.** collection trigger (orders, mode CREATE) → `manual` (assignees `[1]`, form `f1` with actions `resolve`/`reject`, both status 1) → `condition` (`{{$jobsMapByNodeKey.<manual key>._}} == "resolve"`, `rejectOnFalse: false`) → true branch: `request` node POSTing the gateway's client-request envelope to `/api/orders.fulfill` with `{{$context.data.id}}` variables; false branch: `update` node writing `status: failed, error: 审批驳回`. Both manual actions carry RESOLVED because a REJECTED job status ends the execution before any branch could run — branching on the chosen action key keeps the reject path reachable. The manual→condition main chain additionally needs an explicit `downstreamId` write: declaring `upstreamId` alone leaves the execution ending at the manual node (branch children attach by `upstreamId` + `branchIndex`, main-chain siblings do not). DSH's fulfill pipeline already writes every status back at the source, so the approve branch needs no extra update node.

**Attachment delivery is part of fulfill, with the local file as cache copy.** After the PDF lands under `workspace/deliverables`, the pipeline streams it through `attachments:upload` (multipart, field `file`) and hangs the returned attachment id off the order row's `deliverable` attachment field (a `belongsToMany` with `interface: attachment`, created by the setup script alongside the plain columns). The storage-relative url (`/files/...` on 2.2.6) is stored as `deliverableUrl` and projected through the orders API and the order tools; an upload or attach refusal fails the whole run into the existing `failed`-with-cause compensation — a delivered order without its attachment at the source would misreport the record.

**Collection definitions avoid timestamp columns.** NocoBase collections carry `createdAt`/`updatedAt` as system DATE columns; re-declaring either name as a string field replaces the column type and makes Sequelize reject its own automatic timestamp writes (`string violation`). The five seed collections declare business fields only; the seed's ISO strings still write into the system DATE columns. Numeric columns are `float` (`number` is not a field type).

**Idempotency is probe-then-create per artifact; reset is drop-database.** Collections, the seed, and the workflow are each checked for existence and kept; the API key is re-issued per init run (same-named keys are revoked first so the `.env` credential is the only live one). `reset` drops the database and re-runs install + init — the one guaranteed-clean path.

## Consequences

The real-track e2e (`nocobase-track.e2e.ts`) runs the whole journey against the live backend — discovery over the real collections, a real order row, the manual task resolved through the workflow-tasks API, the request-node callback into a DSH-side endpoint serving the `orders.fulfill` RPC semantics, PDF landing, and a byte-equal comparison between the local deliverable and the NocoBase-served attachment — self-skipping with an explanatory test when the backend or credentials are unreachable. It retargets the workflow's request node to its own callback port (3080 when free, ephemeral otherwise) and restores the configured url afterwards, so the test never depends on a long-running `dsh web`. The mock and its specs moved with the corrected wire, so the keyless track and the real track now exercise the same client behavior. `NocoBaseClient.get` returning `undefined` (instead of throwing 404) simplified the orders seam's missing-row handling. Discovery translates the query into `$includes` substring filters, so whole-sentence queries match nothing — callers (and the e2e) query with terms that actually appear in the seeded fields.

## Alternatives considered

- **Keeping the mock's v1-shaped wire and translating in the client** — two wire vocabularies for one backend; every new endpoint would need a remembered translation rule. The live wire is the cheaper single truth.
- **UI-configured workflow with a verify script only** (the plan's MVP fallback) — the REST payloads turned out to be fully discoverable from the plugin sources, and a scripted workflow survives database resets, so the programmatic path won.
- **A REJECTED-status reject action** — reads naturally, but the execution dies at the manual node and the reject branch (status write-back) never runs; branching on `result._` with both actions RESOLVED is the UI-compatible pattern.
- **Sqlite for the backend** — the sequelize sqlite dialect needs the `sqlite3` native package the checkout does not ship; local postgres (brew) with the stock installer path is the supported route.
