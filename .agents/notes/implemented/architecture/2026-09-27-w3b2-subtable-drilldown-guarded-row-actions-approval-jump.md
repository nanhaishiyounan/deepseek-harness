# Agent Note: W3-B2 drawer subtable blocks, guarded row actions, and the approval jump

Status: implemented

English | [中文](2026-09-27-w3b2-subtable-drilldown-guarded-row-actions-approval-jump.zh.md)

## Problem

B1 made the row drawer open at all, but it stayed a read-only field list: the buyer opening a purchase order saw no order lines (a PO detail without lines is useless to a buyer), BOM showed no components or operations, inspections showed no readings (the P0 "filter entry missing" item unpaid), and the supplier profile showed no certificates/audits/scores aggregate. Rows carried no controlled actions, and approval todos were mutually disconnected from the business documents (the approver could not reach the document; the document holder could not reach the approval progress). Actions also could not be given away freely: engine-governed state fields (doc_status/status/result …) may only advance through wfl/engine verbs — a UI write bypasses the approval anchor (invariant 1).

## Decision

**A subtable block is a second, association-bound TableBlockModel paralleling the DetailsBlock in the drawer's BlockGrid items (D3), and it can only land by rewriting the whole drawer tree.** There is no dedicated "association block" model — the official wire (proven by the kanban associated-records contract) puts `associationName: '<parent>.<hasMany>'` plus `sourceId: '{{ctx.view.inputArgs.filterByTk}}'` in the block's `resourceSettings.init` (the drawer's record id propagates through the view inputArgs). The parent collection must first register the hasMany field (`ensureParentHasMany`; the FK is read from the child's belongsTo `foreignKey`, never guessed). **The shape constraint proven live this batch**: a nested `flowModels:save` persists only the top node as a flat row — deep nodes (tabs/grid/columns) exist only inside the findOne nested payload — so a subtable block can never be saved as an independent row under the drawer's grid (the grid is not a flat row at all). The only landing path is destroy-then-rewrite the ChildPageModel with `children` (`drawerPageTreeFor`'s children channel + `subtableBlockNode`). The block carries its own actions column and row drawer (the two-level drill-down); nested node uids ride the w3b2 prefix for traceability, but rolling an embedded block back means re-running the heal (a prefix destroy cannot reach nested JSON). The four line-item pages (receipt/shipment/count/material-issue) were proven by fields:list + psql to have **no child collection** (each receipt_no covers exactly one row) — no subtable is fabricated and the domain model stays untouched.

**Guarded row actions = state blacklist + scoped Delete + zero deletes on engine documents.** The guarded Edit (`saveRowEditAction`: five-key openView + persisted EditFormModel popup located by `filterByTk: '{{ctx.view.inputArgs.filterByTk}}'`) builds its field list from `fields:list` filtered by a triple blacklist: per-collection explicit lists (14 collections — pur_orders drops doc_status/invoice_status/receiving_status/approved_by/approved_at …), generic state-name fallback (doc_status/status/result/*_status — safe for never-probed collections), and system/relation exclusion. Engine write-back anchors (`approved_by`/`approved_at`, the columns wfl extras reads) are equally banned from manual edit. Delete is configured only on free-state collections (tasks/milestones/kb articles/contacts/maintenance) with the official `deleteSettings.confirm` dialog; engine-governed documents get zero Delete entries — lifecycle rides the engine verbs only.

**The approval jump is a JSRecordActionModel on `clickSettings.runJs`, both directions.** Todo rows carry 前往单据 (a doc_type → route map, APPROVAL_JUMP_ROUTES covering the 10 wfl doc_types; hub_po_purchase_orders deliberately unmapped — the click fails loud with 未配置跳转映射) and business rows carry 审批进度 (to the approval center, URL carrying from/doc_type/doc_id anchor params). **The batch's biggest trap**: a JS row action reads its code from `stepParams.clickSettings.runJs` — `jsSettings.runJs` is the JSBlock contract, and an action written with jsSettings renders fine but does absolutely nothing on click (no request, no error — a dead button; the official `flowSurfaces:addRecordAction type:'js'` wire is the authoritative shape to diff against). Navigation uses `window.location.href` (the runjs allowlist permits window/location) with the prefix resolved from `location.pathname.split('/admin/')[0]` — the :3080 gateway serves under /nocobase while a direct :13000 visit does not; a hardcoded path breaks one of the two. Fixed in passing, a w1 legacy bug: the todo block's `resourceSettings.init.filter` (status=open) is never replayed by the runtime — completed rows leaked under the 我的待办 heading; the w9-proven `tableSettings.dataScope` is the channel the runtime replays.

**Inspection readings seed as history rows, never touching state.** qm_inspection_readings had zero rows since creation (nothing to see on the inspector journey). The seed writes a closed document (QI-W2B1-B10 failed — including one pass=false reading consistent with the failed verdict) and a pending one (QI-2026-0010 — entered, awaiting verdict); status/result stay untouched (invariant 1 bans state writes; reading rows are historical fact).

**The flowModels catalog passed 6000 rows — the fail-closed truncation guard firing was correct; the page size was raised, not bypassed.** Seventeen edit forms (one row per field) + twelve subtable blocks + jumps pushed the catalog past 6000; listFlowModels' truncation refusal (heal probe) and setup-nocobase's w9 snapshot assertion (the reconciliation blocks "vanishing" was truncation) both fired; both page sizes went to 12000 and the truncation guard stays.

## Consequences

Eight parent drawers became workbenches: field details + twelve subtable blocks (order lines/request lines/invited suppliers/quotes/SO lines/plan items/BOM components/BOM operations/readings/certificates/audits/score cards) + row actions, every count reconciled against psql (first PO lines 1=1, BOM-0002 components 4/operations 3, supplier #1 certificates 2/audits 6/cards 4, QI-2026-0010 readings 2=2). The two-level drill-down works (subtable row opens its own drawer, levels=2 live). Every guard negative passes: the PO edit form carries zero state fields (recorded labels: 需求日期/金额/币种/比价依据/承诺到货日/订单号), engine collections carry zero deletes, the free-state Delete shows the confirm dialog and the forensic run cancels it (20→20 rows, nothing destroyed). member (quality_lead) opens the same drawer (2 reading rows) with narrowed actions — 查看/审批进度 only; the edit button is ACL-filtered away (member holds no update grant), and every write path still rides the engine. `setup-nocobase.mts verify` asserts four groups: the twelve associations exist, guarded Edit trees leak zero blacklisted fields (findOne nested-tree walk collecting FormItem fieldPaths), engine collections have no Delete, and both jump directions are in place; the probes (tableRows=99, anomalies=0, AddNew 77/77, card drawers all present) and the nine-step chain s1/s2/s8/s9 plus --assert-ledger (32 balanced groups) show zero regression.

## Alternatives considered

- **Build the jump through the official `flowSurfaces:addRecordAction`** — its wire is authoritative (this batch diffed the clickSettings trap against it), but the button title lands as the uncontrollable `{{t("JS action")}}` default; a hand-written wire diffed against the official shape is the controlled middle.
- **Edit/Delete on subtable rows too** — row-level state is equally engine-governed (a reading's pass is the verdict output, a quote's is_won is the award result); read-only + drill-down is the correct boundary.
- **Fabricate child collections for the four line-item pages** — no child collection exists (receipts/counts/issues are one row per document, psql-proven); inventing one would modify the business-correctness base, which the PLAN forbids.
- **Carry a URL filter so the target table auto-filters to the single row** — v2 table URL-state support is unproven; the anchor params (from/doc_type/doc_id) already make the landing assertable, and row filtering waits for a URL-state probe.
