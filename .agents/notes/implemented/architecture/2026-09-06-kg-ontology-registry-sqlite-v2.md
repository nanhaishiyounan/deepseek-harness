# Agent Note: KG ontology registry and the seven-table SQLite property graph v2

Status: implemented

English | [中文](2026-09-06-kg-ontology-registry-sqlite-v2.zh.md)

## Problem

Batch V3 (plans/nocobase-native-integration/03-batches.md): under the enterprise-KG goal, the v1 graph's "the ontology is a compile-time closed set" became the missing extension point — ten business domains and open evolution cannot fit a 7×7 literal union (the deeper reason behind decision D5 of 2026-09-05 expert-dataset-discovery, "leave the graph ontology alone", was exactly the absence of a type-system extension seam). Meanwhile the single `triples` table lacks confidence/bitemporality/independent provenance/edge properties/aliases/watermarks, so it cannot support the kg-build pipeline's (V4) merge idempotence, incremental consumption, and entity alignment.

## Decision

- **Registry-ization overrules D5, both kernels kept** (C report §6.2): `KbGraphEntityType`/`KbGraphPredicate` literal unions → branded open-set ids (`KgNodeTypeId`/`KgRelationId`, dsh-brand); closed-set validation moves from the tool boundary **to the registry boundary** (`KbGraphRuntime.putTriples` pre-validation; unknown types/predicates refuse with `KB_GRAPH_UNKNOWN_ENTITY_TYPE`/`KB_GRAPH_UNKNOWN_PREDICATE`); "extraction never contains a built-in LLM call" survives untouched (the seam stays a pure storage/query face; LLM work belongs to the V4 kg-build pipeline plugin).
- **Three-layer ontology seed** (`kb-graph/src/ontology.ts`, `builtinOntology()`): five top anchors (Object/Process/Event/Role/Concept, schema.org style) + 19 business-domain classes + the food 7 (extends into the matching domain/top class, `source: 'builtin-food'`). On the predicate side the food direction constraints (formerly per-line JSDoc) move into `constraints: {domain, range}[]` — `uses` (product→ingredient/additive) and `complies_with`/`flags` (dual domains) prove a single-valued domain/range cannot express the v1 semantics, hence the constraint-pair array over the C-report draft's single fields; produces/supplies/contains, shared with domain relations, register once with the union of their legal pairs (source stays `builtin-food`). broader/related are constraint-free hierarchical (SKOS reflexive semantics). `KgOntologySource` adds `builtin-ontology` to the research trio — the enum was short one value once three layers exist.
- **Registry API**: `registerNodeType`/`registerRelation` (ctx.effect disposers + `KB_GRAPH_DUPLICATE_NODE_TYPE`/`KB_GRAPH_DUPLICATE_RELATION`; extends/constraints/inverseOf referential existence fails loud), `nodeType`/`relation`/`listNodeTypes(layer?)`/`listRelations`/`validateEdge` (SHACL-style: three codes for unknown relation / unknown endpoint / direction violation). The seed loads directly in the constructor (no effect, not unloadable).
- **Seven-table DDL** (`kb-graph-sqlite/resources/sql/schema.sql`, per C report §2.2 with two on-site deviations): ①`kg_node_types` ②`kg_relations` (**plus a `constraints_json` column** carrying the full pair set — the single domain/range columns hold only the primary pair, and **both are nullable** to admit constraint-free hierarchical relations) ③`kg_nodes` + FTS5 trigram (external content, 3 sync triggers) + `UNIQUE(tenant, type, natural_key)` merge anchor ④`kg_edges` seven-column UNIQUE (the v1 six-tuple semantics survive + the provenance pair extends it: parallel multi-source assertions each stay idempotent) + bitemporal + three indexes ⑤`kg_aliases` (logical merge; deleting the row undoes it) ⑥`kg_source_runs` (watermark + content hash + run-config snapshot) ⑦`kg_usage_counters`. APP_ID "DSHG" carries over (a versioned evolution of one store identity).
- **SCHEMA_VERSION 1→2, pure rejection** (no migration; pre-release stance): opening a v1 database fails with `schema version 1, incompatible with this build (2); delete the file and rebuild`. Rationale: the AGENTS "backends reject old on-disk formats" constitution + the graph is derived, provenance-traceable data (rebuild restores it) + the v1 six-tuple lacks confidence/bitemporality, so a mechanical migration equals a source replay equals a rebuild.
- **Seed materialization at database creation** (the persistent half of the two-layer registry): `insertBuiltinOntology` writes the 31 types + 23 relations into the registry tables (`INSERT OR IGNORE`; the same statement doubles as the fresh-database seed and the write-path ensure — runtime-registered types materialize on first write, so the registry FKs always hold).
- **The v2 storage face** (`KgStore extends GraphStore`, defined in kb-graph types.ts): `upsertNode` (natural-key anchor first, id anchor fallback; returns the merged verdict), `upsertEdges` (probe + MERGE: confidence takes MAX, fact/props COALESCE to the newer value, tombstones revive to NULL; counts fresh inserts), `subgraph` (recursive CTE; UNION dedup keeps cycles terminating; seeds travel via json_each so the statement stays fully parameterized; min(depth) aggregation; maxNodes+1 probes the truncation signal), `expand` (the hops=1 specialization), `tombstoneBySource` (other sources survive), `putAlias` (idempotent per alias→node; a different node refuses with `KB_GRAPH_ALIAS_CONFLICT`), `putSourceRun`/`getSourceRun` (watermark upsert).
- **The putTriples compat translation**: node minting `kb:${encodeURIComponent(type)}:${encodeURIComponent(id)}`; edge provenance `{sourceSystem:'kb', sourceId: sourcePath ?? graph:derived-anchor}` — a present sourcePath is the anchor itself (the C report's "sourcePath promotes to provenance"), an absent one uses the `graph:`-prefixed six-tuple derivation that preserves v1 idempotence; the read path reconstructs `sourcePath` by that prefix. **Registered behavior delta**: the same six-tuple submitted first without and then with a sourcePath yields two coexisting assertions in v2 (v1: a no-op) — multi-source coexistence is a v2 feature, and the existing consumers (the 30 scenario SKILLs, graph-smoke) replay in one form and never hit it.
- **Equivalent read-path rewrite**: `neighbors`/`twoHopPaths`/`searchEntities`/`stats` rebuild over kg_edges/kg_nodes; twoHopPaths resolves the endpoint minted ids first, then runs the four-branch join (the middle endpoint pins by node-id equality — `UNIQUE(tenant,type,natural_key)` guarantees (type,key)↔node is bijective, so this equals the v1 (type,id) comparisons); searchEntities covers natural_key and name (the v1 id doubled as the name) plus alias hits; stats counts live edges only. Branded values read back always rebuild through the owning-package factories, and write-boundary registry validation guarantees membership.
- **tool-kb snapshot materialization** (touchpoints 7/8): `graphOntologySnapshot(registry)` freezes the active type/predicate lists at tool registration (falling back to the builtin seed when kbGraph is not composed — the tools stay visible and refuse at execution); the parse functions take the snapshot parameter; tool descriptions and the system-prompt enumeration generate from it (descriptions stay pure functions of the frozen snapshot; mid-session registry changes surface next session). graph-smoke.mts reads its 7×7 from the registry filtered by `source === 'builtin-food'` (smoke semantics unchanged) and constructs branded ids through the factories.

## Alternatives considered

- **Single-valued domain/range** (the C report §1.4 draft shape) — rejected: v1's uses (product→ingredient/additive) and complies_with (product/process→standard) cannot be expressed; legal extractions would be refused.
- **putTriples anchoring on sourcePath while the read path drops it** — rejected: `source_path` is an observable contract of the tool face (neighbors returns it); dropping it breaks equivalence.
- **Runtime registry aligned with the persistent tables via a sync protocol** — rejected: dual-write skew is a fresh failure surface; ensure-on-write (OR IGNORE) keeps the FKs satisfiable with zero protocol.
- **The KgStore interface as kb-graph-sqlite's own export** — rejected: within a capability seam the Service Definition owns the contract; V4's kg-build will import this same interface as a consumer.

## Consequences

- Tests: kb-graph 14 (registry API/seed/closed-set) + kb-graph-sqlite's 20 existing cases evolved equivalently + 14 new v2-face cases (merge idempotence/revival/cycles/self-loops/depth bounds/truncation/v1 rejection/alias conflict/watermarks) + tool-kb 127 (snapshot signatures) all green; examples/kb-agent 442 show no regression. graph-smoke.mts keeps the 7×7 semantics.
- The 30 food scenario SKILLs run unchanged (the builtin-food seed is equivalent); `KbGraphStoredTriple.rowId` (kg_edges.rowid) and the tenant isolation model survive.
- The V4 handoff is ready: kg-build will inject `kbGraph` + `lakehouse`/`connector`/`kb`/`llm` and drive the full loop through `KgStore.upsertNode/upsertEdges/tombstoneBySource/putSourceRun`; registry upserts (nocobase-derived derivation), the `kg_schema`/`kg_subgraph` tools, and the runtime forwarding of `subgraph` stay in V4.
- The tool enumeration now lists every active type (~31) rather than the food 7 — longer descriptions, correct registry semantics; if extraction quality dilutes, V4 can filter the snapshot by layer/source (graph-smoke already demonstrates the pattern).
